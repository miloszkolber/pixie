# Retained features and Go cutover

This is the mandatory coverage inventory. It owns feature migration decisions; execution.md tracks implementation. A source-language rewrite is not feature parity. The existing TypeScript service calls SDK methods that are not all exposed by Pi's subprocess RPC. Porting prompt/stream/abort while dropping login, native settings, MCP administration or UI lifecycle would be a regression even if the Go binary builds.

## Completion policy

Every row below is retained unless it explicitly describes an already unsupported or new optional feature. Record source/callers, request/result/event fixtures, implementation route, capability, test IDs and both-deployment evidence for each row. API-01 must exhaustively map dispatchers to these rows; CI fails if a used method has no row or a advertised method has no handler/test. New discovered retained methods extend this matrix; they are not deleted as cleanup.

A disabled control with a native-TUI instruction is an honest compatibility fallback, NOT equivalent web functionality. The old implementation stays available during migration until the retained web feature has a tested replacement or the user explicitly approves that particular reduction. No blanket approval of a Go rewrite authorizes feature removal.

Both binaries must pass the same profile fixtures. Go completion is blocked by an uncovered mandatory retained feature. Work on independent rows can continue while an exact upstream gap is investigated. Never report full parity from a core-chat-only test or a green compiler.

## Supported profiles

**V — Vanilla RPC.** Existing Pi executable, native settings/resources, no Pixie bridge or optional package. Required core chat, session history, model/thinking selection, images, native lifecycle and supported native RPC UI primitives work. Missing provider administration is not global incompatibility. Existing native extensions continue to load normally if the operator installed them.

**A — Native administration bridge.** An explicitly enabled, small generic Pixie bridge runs inside the selected Pi process using public extension/package APIs from that installation. It provides versioned administration or observable lifecycle additions absent from native RPC. No private SDK, alternate agent loop, global config injection or extra always-running JS daemon. Bridge absence leaves V functional.

**M — Native MCP integration.** The operator's supported native MCP client owns discovery, connection and execution. The generic bridge can register/scoped-administer connections through its public APIs; Go never implements a competing Pi MCP client. Native tools can work when Pixie's MCP administration capability is absent.

**W — Workspace modules.** Browser, Canvas and Design are independently enabled application capabilities. Panels/tool availability/worker health are separate states. M is required for native agent tool access, not for every human panel operation.

The first candidate native baseline is Pi 0.85.1. Verify the actual published artifact and installed distribution. Npm and standalone-binary installations can expose different import/runtime surfaces; record them as separate tested profiles. A reported version string alone is not proof that a public API exists.

## Concrete bridge implementation route

The administration bridge is an optional native Pi extension, not a background TypeScript replacement for the Go assistant. Keep its source under `assistant/bridge/` and embed the small compiled/source asset in both Go binaries. On explicit enablement, materialize content-addressed read-only assets under assistant-owned private storage and pass the path through Pi's documented extension-loading argv for that child. Do not install it into global/project discovery or edit native settings to make it persistent. Do not load it in V-only acceptance fixtures.

Use a dedicated inherited duplex descriptor for Go-to-bridge messages, with a private per-child nonce/epoch handshake, strict versioned JSONL frames and bounded I/O. Keep administration messages out of native prompt text, stdout, tool logs and transcripts. The bridge closes the descriptor before descendants can inherit it where the runtime permits; test descriptor inheritance and fail enablement if authority can leak to unintended children. No broad HTTP listener, shell-eval command, exported credential blob or arbitrary method dispatch.

Only explicitly allowlisted admin/lifecycle methods are callable. The bridge imports public APIs from the selected Pi installation, never a bundled or independently installed SDK copy. Verify module origin and runtime version during bridge startup; it must fail with `bridge_unavailable` rather than search a random global package. Do not require Node/Bun beyond the selected installation's native extension runtime. For distributions that cannot resolve the necessary public exports, mark A unavailable while V remains functional and record the profile limitation.

Use an on-demand native `--no-session` administration context for explicit global operations when necessary; session-scoped operations bind to the actual managed session context. Dispose it within the same supervisor bounds. Loading an admin context can execute native user extensions, so it is an explicit operation, not read-only doctor/catalog behavior. Do not start a second execution session solely to inspect saved configuration.

The inspected native public package exports ModelRuntime, SettingsManager/resource interfaces and extension APIs, but that alone does not prove every API is accessible from every distribution or the active extension context. BRIDGE-01 verifies import origin, live context access, native lock identity and runtime hooks in independent npm and standalone installs before claiming A support.

For provider/auth operations, delegate the native ModelRuntime implementation including callbacks, OAuth/device flow, refresh/logout and storage. Use real native context/providers where needed; do not initialize a reduced registry that omits project/extension providers and call it complete. Form a separate protected UI/auth interaction channel, bound to its initiating authenticated client, with no model transcript persistence.

For extension settings use the native public storage/resolver interface already exercised by the TypeScript implementation; preserve compare-and-set semantics and native lock identity. Package configuration and loaded runtime state are different results. Never auto-install or roll back a saved change because loading later fails.

For native MCP, relay the adapter's documented versioned runtime APIs; register session credentials only after verified native session identity. Clean registrations on lifecycle transitions and do not reuse a closure across fork/clone. The existing code reaches `ctx.session.agent.state.tools` for some proxy calls; that private/live SDK route must NOT be assumed available from an ordinary extension. BRIDGE-02 must use a supported adapter API or explicitly report the missing operation. Do not replace it with a second client or deep private import.

## Known public-RPC fidelity limits

Pi 0.85.1's inspected rpc-mode.ts implements setWorkingMessage as a no-op; getEditorText returns an empty string. Dialog signal/timeout cleanup removes a request locally without a request-specific cancellation frame in that implementation. Therefore plain event forwarding is not enough to preserve the existing bridge's full UI behavior.

Preserve known deadlines in V and never state that an answer has been accepted by the native tool merely because it was forwarded. A child restart invalidates pending requests. For precise same-child cancellation and working hints, first test documented public lifecycle hooks with exact request identity. Public ui_prompt spans are not automatically the same identity as RPC dialog IDs; do not correlate by timing/title. Where a supported bridge cannot provide the needed event, prepare a narrowly scoped upstream RPC addition and pin a released implementation once tested. Do not monkey-patch private runner/UI internals.

FC15 remains a release/cutover gate for retaining that web behavior; no full-parity claim until evidence or explicit user approval of the specific limitation. Terminal factories already unsupported by the current interface are not a new feature-loss gate, but their limitations must remain visible. Basic V chat is still required and implementable without those additions.

## Fallback and cutover procedure

1. Capture the existing behavior and its tests for every FC row before replacing it.
2. Implement V and both executable compositions. Keep v1/v2 controller adapters explicit during migration.
3. Establish the bridge/native adapter feasibility tests and implement A/M rows using supported surfaces. Do not wait until after deleting TypeScript to discover missing APIs.
4. For unavailable rows, provide a clear disabled state and native-TUI configuration route, record distribution/version/API/reproduction and keep the legacy host selectable for users who need the retained web behavior. Never start both as writers to the same session.
5. Retire the legacy host/package only when retained rows pass in their declared supported profiles, or after explicit approval of individually named reductions. Existing native settings/transcripts are not converted into Pixie-specific state.

A blocker record contains FC ID, affected native distribution/version, missing public symbol/event, isolated reproduction, attempted supported alternatives, exact user-visible limitation, owner and release consequence. Tests/mocks that bypass the missing public API do not close the blocker. Upstream submission and dependency updates follow ordinary approval rules.
