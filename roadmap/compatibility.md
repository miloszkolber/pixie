# Compatibility and no-loss cutover

Owner A/B, with E for integrations and G for release. This is the binding feature-preservation contract. Family summaries in other plans do not waive these requirements.

## What Go parity means

The language rewrite is not the product requirement. The requirement is to keep retained user-visible behavior while changing the assistant's implementation and making the selected host Pi authoritative. Porting chat and declaring every difficult function unsupported is not parity.

Do not hide feature loss behind Go parity means: do not remove provider login, resource management, agent editing, MCP connections, plans, liveness or recovery simply because native JSONL RPC does not expose the SDK calls used today. A disabled control and instructions to use the terminal are honest diagnostics, but they are not an equivalent replacement for a working Web UI action.

No feature reduction is approved by this roadmap. Cutover requires an implemented/tested equivalent for each retained feature in its supported profile, or a separately recorded user decision identifying the exact reduction. An optional integration remains optional; it still has to work when enabled in a supported configuration. Existing terminal-only limitations can remain explicitly unsupported without being counted as new regressions.

## Support profiles

**Vanilla:** independently installed compatible Pi, no optional extensions or Pixie bridge. Native chat/history/model/thinking/images/Stop/reopen/clone/fork/compaction and safely readable workspace remain functional. Pi may have no configured provider: navigation/setup guidance/history still work, and sending explains the missing provider. Basic operation cannot require provider administration, MCP, agent authoring or a bridge capability in the handshake.

**Managed integration:** the same Pi installation, plus an explicitly enabled generic native bridge where native RPC lacks retained administration. The bridge recovers Web UI administration and session integration without a second agent loop, duplicated provider implementation or hidden bundled SDK. It is optional for Vanilla, not an excuse to omit the managed profile from release tests.

**Optional native tools:** operator-installed MCP adapter, delegation, todo/plans, web tools, Signet or local-model support. Test enabled and absent cases. Do not install this bundle automatically, make its absence a startup failure, or certify arbitrary versions from a package name.

The first candidate Pi baseline is released 0.85.1. It is a conformance target, not an assertion that all commands work on every binary distribution. Record npm/standalone packaging, actual executable/version and complete supported operations separately. Newer releases get an upstream smoke lane until accepted into the release-blocking matrix.

## Generic native bridge: bounded implementation path

API-03 is an early feasibility task, before broad SDK deletion. Native RPC is preferred wherever sufficient. For gaps, prototype one opt-in bridge loaded by the selected Pi through its supported extension mechanism; no feature-specific Canvas/Design extension and no second Pi SDK installation.

The bridge runs inside that Pi process and uses its public extension context, native event bus and public APIs from the same installed Pi package. Resolve the package from the selected executable installation, never from Pixie's development node_modules or an unrelated global package. Confirm exports/version identity for npm and standalone Pi separately. The inspected public ExtensionContext does not expose the whole AgentSession/ModelRuntime; do not assume an internal object exists or deep-import implementation files to bypass that limitation.

Use an authenticated private local control channel separate from model tool arguments, conversation text and native stdout. The candidate is a per-child Unix socket beneath a mode-0700 runtime directory, with a boot-scoped credential delivered outside argv and mode-0600 socket permissions. The host sends an allowlisted typed operation and context, not executable JavaScript, shell commands or arbitrary filesystem paths. Responses use the same error/deadline/redaction rules; no public listener or independent daemon is introduced. Test a missing bridge, failed handshake, stale generation and shutdown cleanup.

Explicit opt-in loads the reviewed bridge for managed Pi children only. Do not rewrite native settings, auto-install packages or silently load it in independent TUI sessions. It may be embedded as a trusted versioned asset in both release binaries and materialized only on opt-in; this is not a hidden JavaScript runtime. The selected Pi executes it. Source/asset hash and protocol version appear in diagnostics; no update-time network download.

Administration must call installed Pi's supported auth/settings/resource interfaces, preserve its locking and avoid resetting process-global providers under unrelated sessions. Reuse native bus protocols for MCP and liveness. Never turn an in-memory JS function or disposal handle into a JSON capability merely by serializing it; bridge-side registrations own those handles and release them on generation changes.

API-03 passes only when real independent Pi demonstrates CP-07/08/09/11/12/16 missing operations without a replacement SDK, protocol pollution, secret leakage or cross-session state reset. Where the public API is insufficient, record the exact missing export/context operation, version/distribution and minimal upstream proposal. A bridge is a planned path, not already proven parity.

## Gate and fallback rules

Implement Vanilla and the shell in parallel with API-03. Keep the existing SDK host selectable for development/transition until managed parity is proven; never start both against the same session. Its presence does not complete the Go release. Do not ship a hidden legacy runtime inside either single Go binary.

For an unsupported installation/profile, keep the shell and native core available, display the missing capability, and link to native setup or a supported installation. This is degraded-mode UX, not a waiver for the release's supported managed profile. No reduction is accepted merely because the UI describes it clearly.

Before CUTOVER-01, every CP row has exact method classification, implementation, passing observable tests on both compositions, supported-version evidence and migration/rollback evidence where state changes. New commands not in the table must still be classified by API-01. Any failed required row blocks cutover. A user-approved reduction must identify lost behavior, affected profiles, fallback, retained data, replacement tests and approval reference; none is preapproved here.
