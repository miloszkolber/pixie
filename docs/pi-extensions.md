# Pi extensions

The assistant loads normal Pi resources through `DefaultResourceLoader`. Install packages using Pi's native package commands and configure them through Pi settings. File extensions, package resources and project resources need no Pixie wrapper or marker to execute. Optional application services require a supported API, but ordinary tools and `ctx.ui` calls do not.

| Optional native package or resource | Added functionality |
| --- | --- |
| `pi-mcp-adapter` | Native MCP proxy, with optional Pixie administration through public runtime events |
| `@juicesharp/rpiv-todo` | `todo` tool and `/todos` command |
| `@juicesharp/rpiv-web-tools` | `web_search` and `web_fetch` |
| `@juicesharp/rpiv-ask-user-question` | `ask_user_question` using generic UI dialogs |
| Signet managed file | Native memory tools and lifecycle hooks |
| `@mjakl/pi-subagent` | Native `subagent` execution |

These are optional examples tested by the repository, not an installation bundle. A different extension can execute without being added to this table.

Project trust follows native Pi: project-local resources load only when the project has no trust-requiring resources or the trust store explicitly trusts it (`ProjectTrustStore`, same default-deny as Pi without an interactive prompt). Untrusted project extensions never execute, while user and global extensions load normally; the Extensions screen reports the trust state. Recording trust and reopening the session picks it up with no other configuration change.

Agent definitions live in `<agentDir>/agents/*.md` and `<project>/.pi/agents/*.md`. Pixie's application API provides Markdown CRUD (`pi.sources.*`) and `@agent` mentions without registering model tools. Frontmatter contains `name`, `description` and optional `model` (`provider/model` or a model ID within the inherited provider). The body supplies task instructions. Edits preserve unspecified frontmatter, including the model. Names use letters, numbers, spaces, underscores or hyphens (up to 80 UTF-8 bytes), and each complete file is limited to 64 KiB. Invalid files produce diagnostics while valid definitions remain available. Editability does not establish execution eligibility, which is reported as unknown and remains owned by the installed execution extension's discovery, trust and override rules.

## Native inventory

Settings → Extensions separates saved native configuration from loaded extensions. Inventory reads use `pi.nativeExtensions`, which checks project/root/session ownership and projects the assistant's `pi.extensions.list` response. Configured packages come from Pi's `DefaultPackageManager.listConfiguredPackages()`. Resource resolution uses its public `resolve()` API with missing-package installation explicitly skipped. Actual loaded resources, source metadata, tools, commands and failures come from the resident session's public `resourceLoader.getExtensions()` API. Installed package manifests supply configured-package names and installed versions where available. Pi's loaded-resource metadata does not supply package versions, so loaded versions remain unknown rather than inheriting the version of a potentially newer on-disk package. Interface support remains unknown.

The reader scope is explicit: the selected resident session, configured project resources without a selected session, a non-resident session whose loaded inventory is unavailable, or the existing assistant service context when no project is selected. Inspection never creates, reopens or reloads a session and never imports extension code. Saved configuration can differ from loaded resources. Pi resolves user/project precedence and native filters. Missing sources remain in the configured inventory rather than being silently installed. Load failures expose source locations and safe categories, not raw exception snippets, environment or secret configuration. `pi.config.extensions.*` and `pi.session.extensions.*` remain MCP connection administration and are not this inventory.

For legacy global npm installations, Pi can issue its configured package manager's `root -g` metadata query. Inventory never requests installation, updates or package lifecycle commands.

## Native configuration and deferred reload

“Enable on next load” and “Disable on next load” save a confirmed change in the resource's existing user or project scope. The browser method is `pi.nativeExtensionConfigure`, backed by `pi.extensions.configure`. An opaque resource key and scoped revision bind the request to the inspected native resource. The assistant previews the result with Pi's resource resolver, then uses public `SettingsManager` setters for extension paths or package extension filters. Other package resource filters and unknown settings keys remain intact. Native `+path` and `-path` filters select exact resources. Explicitly empty package extension filters remain empty for other resources when one extension is enabled.

The public `SettingsManager.fromStorage()` boundary supplies a locked compare-and-set write using Pi's proper-lockfile identity. The native setter merges the current file, and atomic replacement preserves its mode. Concurrent changes to native extension/package configuration reject the save. Unrelated concurrent settings edits survive. Malformed settings, non-regular settings targets, unsupported native filter changes and changes that would alter other resources are rejected rather than overwritten. Missing resources are never installed. Static CLI resources, including `--llama`, are not editable through these controls.

Saving is not loading. A successful save reports `saved: true`, `loaded: false` and `reload: deferred`. A save with an unconfirmed transport outcome requires inventory refresh before retry. A later native load failure does not silently roll back the saved configuration. Inventory shows the failure separately. Disabling a loaded extension does not remove its current tools, MCP registrations, dialogs or passive UI from existing sessions.

“Check session reload” calls `pi.nativeExtensionReload` / `pi.extensions.reload`. It never stops work. Active requests, streaming, native tool activity, Bash, pending dialogs and registered background liveness report `session-busy`. Non-resident sessions report `session-not-resident` without opening them. Idle sessions report `sdk-loader-install-policy` and remain unchanged. Repeated checks neither add listeners nor replace capabilities or MCP runtimes.

In-process reload is gated by the pinned Pi 0.85.1 implementation: `AgentSession.reload()` calls process-global `resetApiProviders()`, which cannot be used to reload one session safely beside another. Closing and reopening avoids that reset, but `DefaultResourceLoader.reload()` calls package resolution without an install policy callback. A preflight check cannot exclude a concurrent configuration or filesystem change that triggers installation during reopening. The assistant does not patch private loader state, change process-wide environment, or implement a second loading engine to bypass these boundaries. No automatic restart or privileged helper is used. Actual reload, listener replacement and passive-state cleanup remain deferred until a supported no-install loading path is available and verified.

## Extension UI bridge

The host binds every Pi session with a generic UI bridge, so extensions that ask the user through `ctx.ui` work from the Web UI without a terminal. The bridge supports `select`, `confirm`, `input`, `editor` and `notify`, plus ephemeral `setStatus`, `setWidget` (string arrays), `setTitle` and `setWorkingMessage` projections; terminal-only interfaces (raw terminal input, working visibility/indicator chrome, footers, headers, editor components, autocomplete, editor text, `custom` component factories) stay unavailable. Each blocking call carries a request ID, the Pi session ID, the primitive type and the payload, and settles exactly once with the user's answer, a cancellation, or a timeout (30 minutes).

Dialog state stays scoped to the originating Pi session and request ID. Answers for another session, unknown requests and repeated replies are rejected. Select returns the exact offered string, confirm returns a boolean, and input/editor preserve text. Dismissal returns the native cancellation value (`false` for confirm, `undefined` otherwise). Pending dialogs replay on `session.load` and snapshots reconcile the pending set. All clients dismiss an answered request. The browser-to-controller methods are `session.uiReply` and `session.uiCancel`. The controller-to-host methods are `session.uiResponse` and `session.uiCancel`. Historical questionnaire cards are read-only recaps of persisted tool results. The current SDK bridge supplies no reliable tool-call association, so active requests appear in a session-level dialog rather than being attached by tool-name or timing guesses.

Each session allows 16 pending dialogs, with a maximum 30-minute lifetime. Dialog titles are limited to 2,000 UTF-16 units, other text and answers to 8,000, and selects to 24 options of at most 500 units each. Invalid requests fail explicitly rather than leaving a tool waiting on a card that cannot render.

Status entries remain keyed and separate from working messages. Extension titles appear as ephemeral presentation text and never change saved chat names — including when an extension title equals an existing chat name, which renames no tab and no saved chat. String widgets appear in collapsible areas above or below the composer, in insertion order. Status and widget collections each allow 16 keys, keys have at most 128 units, and widgets have at most 32 lines. Passive text is truncated to 2,000 units and ordinary passive updates are limited to 64 per second per session. Clears bypass that rate limit. All text uses escaped browser rendering, not raw HTML. Passive state clears on connection loss and context shutdown, including native reload invalidation, and is not replayed. Closed contexts reject late updates. Coordinated native reload and rebinding are not exposed by this slice.

Composer get/set/paste APIs report unsupported and never overwrite unsent drafts. The multiline `editor` dialog owns a separate draft. Custom TUI factories and widget component factories also report unsupported without executing their factories. An extension may handle an unavailable custom result and supply its own generic-dialog fallback, but this is not guaranteed for every extension.

Stop unwinds blocked UI on every path (prompt cancel, archive, delete, shutdown): the controller dismisses the modal and the host settles the awaiting call, so no run hangs and no orphan modal survives. Extension-owned background work after prompt idle registers generic per-session liveness, which only delays inactive-projection eviction; explicit lifecycle operations still win. Child subagent sessions stay headless: their dialogs never open nested top-level modals in the parent, and progress arrives through normal tool events.

The optional upstream `ask_user_question` tool uses sequential `select`/`input` dialogs in RPC mode and returns its native answer envelope. The host needs no questionnaire-specific event forwarding.

The optional native subagent extension owns child execution and execution-time discovery. Its project definitions apply only when the project is trusted and override user ones. Progress updates and final details project through the generic tool path onto the child-run card, including parallel calls. Pixie owns only Markdown authoring.

Additive application services can register through `pixie:capability:v1`, defined in `assistant/src/capabilities.ts`. This is separate from native tool discovery and is not required to execute an extension.

The `rpiv-web` search backend is operator-owned external configuration. Provider selection, API keys, and the SearXNG endpoint live in `~/.config/rpiv-web-tools/config.json` and provider environment variables (`WEB_SEARCH_PROVIDER`, `SEARXNG_URL`, per-provider `*_API_KEY`); the default is self-hosted SearXNG at `http://localhost:8080`. Pixie never reads or writes this config. The upstream `web_fetch` SSRF guard refuses loopback and private targets, so it cannot reach Docker-local loopback services; this protection is retained, not weakened.

Global MCP changes apply on subsequent session initialization. Session membership is stored separately. Removing a connection removes only its tools. Unavailable connections are reported without replacing Pi's core tools.

## Pi-native MCP client

Pi loads the operator-installed adapter once; the adapter is the only MCP runtime. The assistant injects a thin administration bridge (`assistant/src/extensions/mcp-admin-bridge.ts`) into its sessions; it detects the public `pi-mcp-adapter:runtime-snapshot:v1` response without creating a server or importing the adapter. The model calls native `mcp`, and upstream's optional `mcpScript` follows native settings. Session attachment registers proxy-only servers through `pi-mcp-adapter:runtime-register:v1`. Identical attachments are idempotent, conflicting definitions fail closed, and idle reload restores membership and controller attachments. Explicit removal/addition replaces a managed definition. Browser-specific registration remains first-wins. Legacy administration does not rewrite native `{mcpServers: ...}` configuration. The host CLI aligns `PI_CODING_AGENT_DIR` with its selected agent directory and suppresses desktop viewer launching by default. The public event integration is tested against adapter 2.32.1.

The bridge advertises one application capability, `mcp`. Without a compatible native runtime it stays unavailable, and basic Pi sessions still work.

## Local llama.cpp provider

`--llama` loads the Pi SDK's own built-in llama.cpp extension unchanged. The pinned SDK does not export its built-in extension barrel from the public index; an additive upstreamable export patch publishes the `./extensions` subpath (applied by Bun `patchedDependencies` and, for standalone installs, the assistant postinstall), and `assistant/src/extensions/llama.ts` imports the factory through that public path. A missing patch degrades to unavailable, while a requested `--llama` profile fails loudly at startup. It registers the local provider and `/llama` command. Model selection uses `pi.providers.*` and `session.configure`. The operator supplies `LLAMA_BASE_URL`. Auth uses the stored credential, `LLAMA_API_KEY`, or the dummy key `local`. The `/llama` management command requires a terminal. Provider registration, catalog refresh and inference are headless.

## Signet memory

Signet loads through Pi's own `<agentDir>/extensions` discovery once the operator installs it (`signet setup` writes the managed `signet-pi.js` file). Loaded inventory reports its actual tools rather than a marker. Its daemon lifecycle hooks stay fail-open while the daemon is unreachable, and auto-recall arrives as hidden context. The daemon endpoint (`SIGNET_DAEMON_URL`, default `http://127.0.0.1:3850`), `signet.json` and per-session `SIGNET_ENABLED=false` remain operator-owned. Pixie never reads or writes them and connects no MCP for Signet.
